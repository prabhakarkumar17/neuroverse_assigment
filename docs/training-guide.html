1. How to use this guide

You know Java. That is a large head start and it also sets a trap: much of Kotlin looks like Java with less typing, so it is tempting to write Java in Kotlin syntax and move on. The parts that matter — null safety, sealed types, coroutines, immutable state — are not shorthand. They move whole categories of bug from runtime to compile time. This guide is organised around those differences rather than around a feature list.

Every concept is tied to real code in the delivered app, so nothing here is abstract. Where a file is named, open it: the source is commented to be read alongside this document.

Reading order

  • Presenting this project tomorrow? Read Part 6 (architecture), Part 8 (the app end to end), and Part 11 (likely questions). That is about 40 minutes and covers everything you would be asked.
  • Learning Android properly? Read in order. Parts 2–5 are the foundation; Parts 6–10 apply it.
  • Stuck on specific syntax? Part 3 is organised as a Java→Kotlin lookup table.
A note on the three-sided comparison Throughout, code appears in pairs: the Java you would write, and the Kotlin this project does write. The point is never that Kotlin is shorter. It is which mistakes each version makes possible.

2. The Android mental model

Before any Kotlin, you need the model the OS imposes. Most Android bugs written by experienced backend developers come from assuming the app controls its own lifetime. It does not.

2.1 What an Android app actually is

A JVM server application has a main(), runs until it is stopped, and owns its process. An Android app has none of those properties.

An APK is a zip containing compiled Dalvik bytecode (classes.dex), resources, and a manifest. There is no main(). Instead the manifest declares components the OS may instantiate, and the OS calls into them when it decides to. Your code is a library that the operating system drives.

The single most important consequence You do not start your app. You do not stop your app. The OS creates your process when something needs it, and destroys it when memory is needed elsewhere — possibly while the user is still looking at it. Every piece of state that matters must survive that, or be reconstructible.

2.2 Processes, and why Android kills them

Android runs on devices with limited RAM and no swap. When memory runs low, the system kills whole processes, ranked by importance:

RankStateKilled?
1Foreground — user is interacting with itAlmost never
2Visible — on screen but not focused (behind a dialog)Rarely
3Service — doing background workSometimes
4Cached — user pressed Home, app still in memoryRoutinely

Rank 4 is the one that breaks naive apps. The user presses Home, opens a camera app, comes back two minutes later — and your process was killed and restarted in between. Android restores the screen they were on, but every object you held in memory is gone.

This is exactly why this app persists its session to encrypted storage instead of keeping the logged-in user in a variable. We tested it: adb shell am force-stop kills the process outright, and the app comes back still signed in.

2.3 The Activity lifecycle

An Activity is one screen, and the only thing the OS knows how to start. It is driven through a fixed sequence of callbacks:

onCreate() created - build the UI. Called ONCE per instance. onStart() becoming visible onResume() foreground - user can interact. Start camera/sensors here. ... the user is using your app ... onPause() losing focus - STOP anything that must not run unseen onStop() hidden - release heavy resources onDestroy() finished - last call (may never arrive if killed)

In this app MainActivity.onCreate() is nine lines: enable edge-to-edge drawing, and hand off to Compose. Everything else lives in ViewModels, which is deliberate — anything written inside an Activity needs a device to test.

The rotation trap Rotating the device destroys and recreates the Activity by default. Android treats a configuration change as "the screen is fundamentally different now, rebuild it". Any state held in an Activity field is lost. This is why ViewModels exist: a ViewModel survives configuration changes, because Android deliberately keeps it alive across the destroy and recreate. Try it — rotate the emulator mid-registration and the typed form is still there.

2.4 The manifest

AndroidManifest.xml is read by the OS before any of your code runs. It is the only way to declare what exists. From this project:

<uses-permission android:name="android.permission.INTERNET" />

<application
    android:name=".AuthApplication"        <!-- our Application subclass -->
    android:allowBackup="false"            <!-- a security decision, see Part 9 -->
    android:theme="@style/Theme.NeuroVerse">

    <activity android:name=".MainActivity" android:exported="true">
        <intent-filter>
            <action   android:name="android.intent.action.MAIN" />
            <category android:name="android.intent.category.LAUNCHER" />
        </intent-filter>
    </activity>
</application>

That intent-filter is what puts the app's icon in the launcher. Remove it and the app installs but cannot be opened. exported="true" means other apps may start this component — required for the launcher activity, and deliberately absent from everything else here.

2.5 Resources and qualifiers

Everything under res/ is compiled into a lookup table and referenced through the generated R class: R.drawable.ic_arrow_back, R.string.app_name. The powerful part is qualifiers. Android picks the right file automatically based on device state, with no code:

DirectoryUsed when
res/values/colors.xmlDefault
res/values-night/colors.xmlDevice is in dark mode
res/values-hi/strings.xmlDevice language is Hindi
res/drawable-xxhdpi/Very high density screen
res/layout-sw600dp/Smallest screen width ≥ 600dp (tablet)

This app uses values-night/ for the dark-mode window background. No if-statement is involved: the resource system resolves it.

dp and sp — and why the difference matters

  • px — a physical pixel. Never use it; a 48px button is a thumb-sized target on an old phone and a speck on a modern one.
  • dp (density-independent pixel) — scaled so 48dp is the same physical size on every screen. Use for all layout.
  • sp (scale-independent pixel) — like dp, but also scales with the user's font-size accessibility setting. Use for all text, always.

Sizing text in dp silently ignores every user who enlarged their system font. That is an accessibility failure, and it is a one-character mistake.

3. Kotlin for Java developers

This part is a lookup table. Each section shows the Java you know, the Kotlin this project uses, and — most importantly — which bug the Kotlin version makes impossible.

3.1 val and var

Java
final String name = "Prabhakar";
String count = "0";          // mutable
final List<String> xs = new ArrayList<>();
xs.add("ok");       // still allowed!
Kotlin
val name = "Prabhakar"   // type inferred
var count = 0            // reassignable
val xs = listOf("ok")    // READ-ONLY
// xs.add("x")           // does not compile

val is final. The real difference is in the collections: Java's List is always mutable, and final only stops reassignment of the reference. Kotlin splits the types: List has no add() at all, MutableList does. Immutability becomes checkable.

Default to val Write val everywhere and change to var only when the compiler forces you. In the 34 source files of this app there are 6 var declarations — every one a deliberate piece of mutable UI state.

3.2 Null safety — the big one

In Java every reference can be null, and the compiler does not care. The NullPointerException is so common its inventor called it his "billion-dollar mistake". In Kotlin, nullability is part of the type.

Java
String name = user.getName();
// compiles; may throw at runtime
int len = name.length();

if (name != null) {
    len = name.length();
}
Kotlin
// cannot be null:
val name: String  = "always here"
// CAN be null:
val maybe: String? = null

// maybe.length   -> compile ERROR
val len  = maybe?.length      // Int? or null
val safe = maybe?.length ?: 0 // default
OperatorMeaningIn this project
?Declares the type nullableval user: User? — null means signed out
?.Safe call: returns null instead of throwingdisplayName?.takeIf { it.isNotBlank() }
?:Elvis: value on the left, or fallback on the rightemail ?: "User"
?.let { }Run a block only if non-nullerrorMessage?.let { Text(it) }
!!Assert non-null, throw if wrongUsed once, on a framework value guaranteed present
Treat !! as a code smell !! says "I know better than the compiler". It converts a compile-time guarantee back into a runtime crash, which is the entire problem Kotlin set out to solve. Every !! should be justifiable in one sentence. In this project the only one is this[APPLICATION_KEY]!!, where the Android framework guarantees the Application is present when a ViewModel factory runs.

Platform types: where null safety has a gap

When Kotlin calls Java code, it cannot know whether a returned reference is nullable. Such types are shown as String! and Kotlin trusts you — no check is enforced. Firebase is a Java library, so this is live in our code:

// FirebaseUser.getEmail() is Java; Kotlin sees String!
// We defensively treat it as nullable rather than trusting it:
email = email.orEmpty()        // null becomes ""

This is why FirebaseAuthRepository is careful with displayName and email: those are the exact places where a Java library can still hand you a null.

3.4 sealed interface vs enum

An enum is a fixed set of constants. A sealed type is a fixed set of types, each able to carry different data. That distinction is the whole reason this app's error handling works.

Java
enum AuthError {
  INVALID_CREDENTIALS,
  NETWORK,
  UNKNOWN
}
// Cannot attach a Throwable to UNKNOWN
// only, or a message to one case only.

switch (error) {
  case INVALID_CREDENTIALS: ...
  // forget a case -> silent fallthrough
}
Kotlin
sealed interface AuthError {
  val message: String

  data object Network : AuthError {
    override val message = "No connection."
  }
  data class Unknown(val cause: Throwable?)
      : AuthError {
    override val message = "Try again."
  }
}
Exhaustiveness is the payoff Because the compiler knows every subtype of a sealed type, a when used as an expression must handle all of them — no else needed. Add a new error case and every when in the codebase stops compiling until it is handled. A forgotten case becomes a build failure instead of a silent wrong branch.

data object (Kotlin 1.9+) is a singleton with a sensible toString(). Use object for cases with no data (Network) and data class for cases that carry some (Unknown(cause)).

The Nothing trick

sealed interface AuthOutcome<out T> {
    data class Success<T>(val data: T) : AuthOutcome<T>
    data class Failure(val error: AuthError) : AuthOutcome<Nothing>
}

Nothing is Kotlin's bottom type: it has no instances and is a subtype of every type. So a single Failure class satisfies AuthOutcome<User>, AuthOutcome<Unit> and every other instantiation at once, with no generic parameter of its own. Java has no equivalent.

3.6 Extension functions

Add a method to a type you do not own, without inheritance or a utility class:

// Declared INSIDE FirebaseAuthRepository, so it is private to this file:
private fun FirebaseUser.toUser(fallbackName: String = ""): User {
    return User(id = uid, name = ..., email = email.orEmpty())
}

// Call it as if Firebase had written it:
val user = firebaseUser.toUser()

Nothing is patched at runtime — it compiles to a static method taking the receiver as its first argument, exactly like a Java utility. The gain is that it reads in the right order and is scoped: this one is invisible outside the file.

3.7 Lambdas and higher-order functions

Java
button.setOnClickListener(
  new View.OnClickListener() {
    @Override public void onClick(View v) {
      doThing();
    }
  });
Kotlin
// Function type as a parameter:
fun PrimaryButton(onClick: () -> Unit)

// Trailing lambda goes outside the parens:
Button(onClick = { doThing() }) {
    Text("Tap")
}

Two rules explain most Compose code:

  1. Trailing lambda — if the last parameter is a function, it can be written after the closing parenthesis. Column(modifier = m) { ... } is just Column(modifier = m, content = { ... }).
  2. it — a single-parameter lambda names its argument it implicitly.

Method references work as in Java: viewModel::onEmailChange is Kotlin for viewModel::onEmailChange.

3.10 when

when is switch without fallthrough, and it is an expression, so it returns a value:

// From Validators - replaces a chain of if/else-if:
fun validatePassword(password: String): ValidationResult = when {
    password.isEmpty()            -> Invalid("Password is required.")
    password.length < 8           -> Invalid("At least 8 characters.")
    password.none { it.isDigit() } -> Invalid("Must contain a number.")
    else                          -> Valid
}

// Type-matching form, with automatic smart-casting:
when (e) {
    is FirebaseAuthWeakPasswordException  -> AuthError.WeakPassword
    is IOException                        -> AuthError.Network
    else                                  -> AuthError.Unknown(e)
}

Smart casts: after is FirebaseAuthWeakPasswordException, the compiler knows the type — no cast needed. Java 16+ pattern matching finally does this too.

3.11 Properties replace getters and setters

// Computed property - no backing field, recalculated on read:
val initial: String
    get() = name.trim().firstOrNull()?.uppercase() ?: "?"

// Private mutable, public read-only - the key pattern in every ViewModel:
private val _uiState = MutableStateFlow(LoginUiState())
val uiState: StateFlow<LoginUiState> = _uiState.asStateFlow()

That last pair is the Kotlin equivalent of returning Collections.unmodifiableList() — callers can observe, only the owner can change. The _ prefix for the private backing property is the official Kotlin convention.

3.12 Collections

Java Streams

Kotlin

// Template - no concatenation, no String.format:

// Raw string - no escaping. Compare the regex both ways:
// Java:   "^[A-Za-z0-9._%+\\-]+@[A-Za-z0-9.\\-]+\\.[A-Za-z]{2,}$"
// Kotlin: """^[A-Za-z0-9._%+\-]+@[A-Za-z0-9.\-]+\.[A-Za-z]{2,}$"""

For regular expressions, raw strings alone justify the feature: the pattern reads as the pattern, not as its escaped form.

4. Coroutines: replacing threads and callbacks

4.1 The rule that forces all of this

Two absolute rules 1. All UI work must happen on the main thread.
2. Nothing slow may ever happen on the main thread.

Block the main thread for ~5 seconds and Android shows "App isn't responding" and offers to kill it. This is the ANR (Application Not Responding) dialog.

So every network call must leave the main thread, and its result must come back to it. Java's answers to this were all unpleasant: AsyncTask (deprecated, leaked Activities), raw Thread plus runOnUiThread (verbose, easy to get wrong), or callbacks (which nest).

4.2 The callback problem

Java callbacks
api.register(email, pw, new Callback() {
  public void onSuccess(User u) {
    api.updateProfile(u, name, new Callback() {
      public void onSuccess(Void v) {
        api.sendVerification(u, new Callback() {
          public void onSuccess(Void v) {
            showHome();              // 4 levels deep
          }
          public void onError(E e) { show(e); }
        });
      }
      public void onError(E e) { show(e); }   // repeated
    });
  }
  public void onError(E e) { show(e); }       // repeated
});
Kotlin coroutines
// The real code from FirebaseAuthRepository:
suspend fun register(...): AuthOutcome<User> = runAuth {
    val result = firebaseAuth
        .createUserWithEmailAndPassword(email, password)
        .await()

    val firebaseUser = result.user
        ?: return@runAuth Failure(Unknown())

    firebaseUser.updateProfile(
        userProfileChangeRequest { displayName = name }

4.3 What suspend actually does

A suspend function can pause without blocking its thread. At each suspension point the coroutine saves its state, releases the thread so other work can use it, and resumes later — possibly on a different thread.

There is no magic. The compiler rewrites a suspend function into a state machine: it adds a hidden Continuation parameter and turns the code between suspension points into the branches of a switch. If you have written a non-blocking server with a callback state machine by hand, the compiler is now doing that transformation for you.

suspend is also a contract enforced by the compiler A suspend function can only be called from another suspend function or from a coroutine. You cannot accidentally call the login network request from ordinary synchronous code — that is a compile error, not a runtime ANR. The signature itself tells every caller "this may take time".

4.4 Dispatchers: which thread pool

DispatcherBacked byUse for
Dispatchers.MainThe Android main/UI threadUI updates. viewModelScope defaults to this.
Dispatchers.IOA large pool (~64 threads)Disk, network — work that waits
Dispatchers.DefaultPool sized to CPU coresWork that computes — parsing, sorting

withContext switches dispatcher and switches back automatically:

// From LocalAuthRepository. PBKDF2 at 210,000 iterations takes ~100ms and
// SharedPreferences writes hit the disk - both would jank the UI thread.
private suspend fun <T> io(block: suspend () -> T): T =
    withContext(Dispatchers.IO) { block() }
A detail worth knowing Hashing is CPU work, so Dispatchers.Default would be the textbook choice. It is on IO here because the same block also writes to disk, and mixing one short CPU burst into the IO pool is harmless. The rule of thumb: IO for work that waits, Default for work that computes.

4.5 Structured concurrency

Every coroutine belongs to a CoroutineScope. Cancel the scope and every child coroutine is cancelled with it. This is what makes coroutines leak-proof where raw threads were not.

// In every ViewModel in this app:
viewModelScope.launch {
    val user = repository.restoreSession()
    _authState.value = ...
}

viewModelScope is cancelled automatically when the ViewModel is cleared. So if the user leaves the screen mid-login, the request is cancelled and nothing tries to update a destroyed UI. The classic Android leak — a background thread holding an Activity reference and calling back into it after destruction — is structurally impossible here.

4.6 Flow and StateFlow

A suspend function returns one value. A Flow emits many over time — the coroutine equivalent of RxJava's Observable.

StateFlow is the variant this app uses everywhere. It is a Flow that always holds a current value:

private val _currentUser = MutableStateFlow<User?>(null)   // writable, private
override val currentUser: StateFlow<User?> = _currentUser.asStateFlow()  // read-only
LiveData (older)StateFlow (used here)
Lifecycle-awareBuilt inVia collectAsStateWithLifecycle()
Needs AndroidYes — untestable on plain JVMNo — pure Kotlin
OperatorsFewmap, filter, combine, debounce...
Always has a valueNoYes

That second row is why all 46 unit tests run without an emulator.

Why collectAsStateWithLifecycle and not collectAsState

val uiState by viewModel.uiState.collectAsStateWithLifecycle()

Plain collectAsState() keeps collecting while the app is in the background. With a network call behind the flow, that means work continuing behind a locked screen, burning battery for a UI nobody can see. The lifecycle-aware version stops collecting at onStop and resumes at onStart. Prefer it by default.

5. Jetpack Compose: UI as a function of state

5.1 The shift from imperative to declarative

Classic Android UI is imperative: inflate an XML layout, find views by id, then mutate them as things change. Compose is declarative: you write a function that describes the UI for a given state, and the framework re-runs it when that state changes.

Classic Android (XML + Java)
// activity_login.xml declares the views...
// then in code:
EditText email = findViewById(R.id.email);
TextView error = findViewById(R.id.error);
Button submit = findViewById(R.id.submit);

submit.setOnClickListener(v -> {
    submit.setEnabled(false);
    error.setVisibility(View.GONE);
    login(email.getText().toString());
});

void onLoginFailed(String msg) {
    submit.setEnabled(true);        // easy to forget
    error.setText(msg);
    error.setVisibility(View.VISIBLE);
}
Compose
@Composable
fun LoginContent(uiState: LoginUiState, ...) {
    MessageBanner(
        message = uiState.formError,
        type = BannerType.ERROR
    )
    AppTextField(
        value = uiState.email,
        onValueChange = onEmailChange
    )
    PrimaryButton(
        text = "Sign in",
        onClick = onSubmit,
        enabled = uiState.canSubmit,
        isLoading = uiState.isLoading
    )
}
// There is no "update the button" code.
// The UI IS the state.
Why this eliminates a whole bug class In the imperative version, the screen's appearance and the underlying state are two separate things that must be kept in sync by hand. Forget one setEnabled(true) on one error path and the button stays dead forever. In Compose the UI is derived from state, so they cannot disagree. The bug is not fixed — it is unrepresentable.

5.2 Composable functions and recomposition

A @Composable function describes UI. It returns nothing; it emits. When state it reads changes, Compose re-runs it — this is recomposition.

Compose is smart about scope: only functions that actually read the changed state are re-run. But you must write composables that tolerate being called often and in any order:

  • They may run many times per second.
  • They may run in any order, or in parallel.
  • They may be skipped entirely if their inputs are unchanged.
The consequence: composables must be side-effect free Never start a network call, write a file, or navigate from a composable's body — it would fire on every recomposition. That is why navigation in this app goes through LaunchedEffect, which is keyed and runs once (see 5.6).

5.3 State: remember and mutableStateOf

var visible by rememberSaveable { mutableStateOf(false) }

5.4 State hoisting — the pattern used on every screen here

A composable that owns its own state cannot be previewed, tested, or controlled. Hoisting means moving state up to the caller and passing it down, with events going back up. Every screen in this app is split in two:

// STATEFUL: gets the ViewModel, collects state. Cannot be previewed.
@Composable
fun LoginScreen(..., viewModel: LoginViewModel = viewModel(factory = ...)) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
    LoginContent(
        uiState = uiState,                        // state DOWN
        onEmailChange = viewModel::onEmailChange, // events UP
        onSubmit = viewModel::login
    )
}

// STATELESS: holds ALL the layout, owns nothing. Previewable and testable.
@Composable
private fun LoginContent(uiState: LoginUiState, onSubmit: () -> Unit, ...) { ... }

This costs one extra function and makes the entire screen testable. It is also what lets the @Preview annotations render error states in Android Studio without an emulator:

@Preview(showBackground = true, name = "Login - error")
@Composable
private fun LoginErrorPreview() {
    NeuroVerseTheme {
        LoginContent(LoginUiState(formError = "Incorrect email or password."), {}, {}, ...)
    }
}

  • .verticalScroll(rememberScrollState()) — the registration form has four fields plus a button. On a small phone in landscape with the keyboard open, that does not fit, and without scrolling the lower fields are simply unreachable.

5.6 Side effects: LaunchedEffect

Composables must be pure, but real screens must sometimes do something. LaunchedEffect runs a coroutine tied to the composable, re-running only when its key changes:

LaunchedEffect(uiState.isLoginSuccessful) {
    if (uiState.isLoginSuccessful) {
        onLoginSuccess()
        viewModel.onNavigationHandled()   // consume the flag so it cannot re-fire
    }
}

Calling navigate() directly in the composable body would fire on every recomposition and push a dozen copies of Home onto the back stack. Keyed on the flag, it fires once. Resetting the flag afterwards is what stops it firing again on the next recomposition — and there is a unit test asserting exactly that.

5.7 Theming

NeuroVerseTheme wraps the whole app and supplies colours and type through CompositionLocals, so no screen hardcodes a colour:

MaterialTheme(
    colorScheme = if (darkTheme) DarkColors else LightColors,
    typography = AppTypography,
    content = content
)

Dark mode therefore needed no per-screen work — only a second ColorScheme. Note that Material 3's dynamic colour (deriving the palette from the user's wallpaper on Android 12+) is deliberately disabled here: for a corporate auth app the brand colour changing per device is wrong, and screenshots would not match brand guidelines.

6.5 The UiState pattern

Each screen has one immutable data class holding everything it displays:

data class LoginUiState(
    val email: String = "",
    val password: String = "",
    val emailError: String? = null,
    val passwordError: String? = null,
    val formError: String? = null,
    val isLoading: Boolean = false,
    val isLoginSuccessful: Boolean = false
) {
    val canSubmit: Boolean
        get() = email.isNotBlank() && password.isNotBlank() && !isLoading
}
Why one object and not six separate flows With separate flows for email, isLoading and error, each updates independently, so the UI can briefly observe an impossible combination — isLoading = true alongside a success message, for instance. One immutable object swapped atomically can only ever represent a state that actually occurred.

canSubmit being a computed property matters too: it is derived, so it can never drift out of sync with the fields it depends on.

6.6 Unidirectional data flow

User types in the email field │ ▼ onValueChange lambda ──────────► viewModel.onEmailChange("a@b.com") │ ▼ _uiState.update { it.copy(email = ...) } │ ▼ StateFlow emits a NEW LoginUiState │ ┌──────────────────────────────────┘ ▼ collectAsStateWithLifecycle() receives it │ ▼ Compose recomposes LoginContent with the new state │ ▼ The field shows the new text

State flows one way only. The UI never mutates state directly; it reports events. This is why a bug is always traceable: there is exactly one place any given piece of state can change.

6.7 Dependency injection, and why Hilt is absent

Hilt is the standard recommendation for large Android apps, and you should learn it. It is deliberately not used here:

  • This app has one dependency worth injecting. Hilt would add an annotation processor, a Gradle plugin, modules and six annotations to solve a 20-line problem.
  • Annotation processing is where build setups break, especially on a brand-new toolchain.
  • Hilt's generated code hides the object graph. ServiceLocator can be read top to bottom, which matters more while you are learning.

Manual DI is a documented, officially-endorsed Android approach, not a shortcut. The property that matters — construction centralised in one place — holds either way. If asked "why not Hilt?", that is the answer: scope, not ignorance.

            popUpTo(0) { inclusive = true }
            launchSingleTop = true

}

Centralising it means a new protected screen is protected by default, rather than protected only if someone remembers to add a check. That is the difference between a security control and a convention.

9. Applied security

Spec section 5 lists nine security requirements. This part explains the reasoning behind each implementation, because "we used PBKDF2" is not an answer — knowing why is.

9.1 Password hashing

Why not SHA-256?

Because it is fast, and speed is the enemy here. A modern GPU computes billions of SHA-256 hashes per second, so a stolen database of them falls in hours. PBKDF2 repeats the hash 210,000 times, turning one guess into 210,000 units of work. Password hashing is the one place in cryptography where you want terrible performance.

Why the salt?

Without one, identical passwords produce identical hashes. An attacker cracks every "Password123" in the database simultaneously and can use precomputed rainbow tables. A unique random salt per user forces each password to be attacked individually. The salt is not secret and is stored alongside the hash.

The stored format

210000:IrmjXRMNX6+QKuyXd7cNUA==:RFNahglW+pwqoU1idAV5+BG7Nn+FUnWu9aFpA/ozZRY=
└─────┘ └──────────────────────┘ └──────────────────────────────────────────┘
iterations        salt                            hash

That is a real record taken from the running app. The iteration count is embedded so that stored hashes stay verifiable after ITERATIONS is raised in a future release — verify() re-derives using the recorded count, not the current constant.

Constant-time comparison

private fun constantTimeEquals(a: ByteArray, b: ByteArray): Boolean {
    if (a.size != b.size) return false
    var diff = 0
    for (i in a.indices) diff = diff or (a[i].toInt() xor b[i].toInt())
    return diff == 0
}

A normal equals returns as soon as it finds a mismatched byte. An attacker who can measure that timing learns how many leading bytes they guessed correctly, and can then solve the hash one byte at a time instead of all at once. XOR-ing every byte and testing only at the end removes the signal.

Be honest about this in your presentation Spec 5 requires passwords to be hashed on the server. The offline mode hashes on the device, which does not meet that clause — it exists so the app runs without a backend. The Firebase path is the one that satisfies spec 5: passwords leave the device over HTTPS and Firebase hashes them with scrypt server-side. Say this plainly rather than letting a reviewer discover it.

9.2 The Android Keystore

Encryption is easy; the hard part is where you keep the key. A key hardcoded in the APK or stored next to the data is no protection at all — anyone who can read the data can read the key.

What the Keystore actually provides The key is generated inside the system keystore — on most modern devices inside hardware (a Trusted Execution Environment or secure element) — and the key material is never returned to our process. We hold an opaque handle and ask the system to encrypt and decrypt for us. Even with a rooted device and a full filesystem dump, an attacker gets ciphertext and a key reference that is useless off that device.

Why AES-GCM rather than CBC

GCM is an AEAD mode: it authenticates as well as encrypts. Alter a single byte of ciphertext and decryption throws instead of returning plausible garbage. That turns silent tampering into a loud, detectable failure. CBC would decrypt modified data happily.

The IV rule

GCM requires a unique initialisation vector per encryption under the same key. Reusing an IV with GCM is catastrophic — it leaks the authentication key, not merely the plaintext. So the code never chooses an IV:

cipher.init(Cipher.ENCRYPT_MODE, getOrCreateKey())  // no IV passed in
val iv = cipher.iv                                   // provider generated a random one
val combined = iv + cipherText                       // store IV alongside ciphertext

An IV is not secret; it only has to be unique. Prepending it to the ciphertext is standard practice.

Verified at rest

Read directly off the device with run-as:

$ adb shell run-as com.neuroverse.authapp.debug \
      cat /data/data/com.neuroverse.authapp.debug/shared_prefs/neuroverse_session.xml

<string name="session_blob">JiHklY8PwFH/kI9sbVrDZzt0UypVQVXr+yxZBlP3wfrwWGRmklQT
WuQkyrZEIrhe2OuvRf2/L94NuODZFDDDe7m43rWaenMuLjoBlxq8UxRs2DIG/agJ8xccuA76...</string>

Opaque. No email, no name, no id recoverable without the device's Keystore.

9.3 Account enumeration — the subtle one

This is the security decision most likely to be questioned as a bug, so it is worth being able to defend.

If the login screen replies "no account with that email" for unknown addresses and "incorrect password" for known ones, it becomes a free tool for discovering who has an account. Feed it a list of addresses and the error messages sort them into registered and unregistered. For a corporate system that leaks your staff list; for a sensitive service it can leak far more.

ScreenBehaviourWhy
Login"Incorrect email or password." for both casesCannot distinguish unknown email from wrong password
Forgot password"If an account exists for this email, a link has been sent."Identical response whether or not the account exists
Registration"An account with this email already exists."Unavoidable — see below

Registration must disclose this: the user cannot be allowed to create a duplicate account, so something has to be said. The standard mitigation is rate limiting, which Firebase applies server-side and which surfaces here as AuthError.TooManyRequests.

Two unit tests exist purely to protect this property, and will fail if someone "helpfully" adds a more specific message:

@Test
fun `scenario 4 - unknown email is rejected with the SAME message as a wrong password`()

@Test

9.5 Backup is disabled on purpose

android:allowBackup="false"

With backup enabled, Android copies SharedPreferences to the user's cloud account. Our session blob is encrypted with a key that lives in this device's Keystore and is not backed up, so a restored copy would be permanently undecryptable anyway. Excluding it outright is cleaner than shipping ciphertext we know can never be read. Both backup_rules.xml and data_extraction_rules.xml additionally name the files, so the exclusion holds on every supported API level.

9.6 What the client can never enforce

Say this out loud when presenting Every validation rule in Validators.kt is a UX convenience, not a security control. An attacker does not use your UI — they call the API directly, or patch the APK. Client validation exists to give instant feedback and avoid pointless network round trips. The server re-validates everything, and that is the half that enforces anything. Spec 5 asks for validation "on both the client and server sides" precisely because the two halves do different jobs.

10.3 Controlling time

viewModelScope runs on Dispatchers.Main, which does not exist on a plain JVM. MainDispatcherRule replaces it with a StandardTestDispatcher, which also hands the test control over time: coroutines queue until explicitly advanced.

This produced the one genuine test failure during development, and the fix is instructive. The first version of the loading-state test was:

vm.register()
assertTrue(vm.uiState.value.isLoading)   // FAILED

It failed because StandardTestDispatcher had not started the coroutine yet, so isLoading was still false. The test was wrong, not the code. The fix was to give the fake a gate the test can hold open, creating an observable in-flight moment:

repository.openGate()        // next call will suspend inside the gate
vm.register()
runCurrent()                 // start the coroutine; it parks in the gate

assertTrue(vm.uiState.value.isLoading)   // now genuinely in flight
assertFalse(vm.uiState.value.canSubmit)  // ← the double-submit guard

repository.releaseGate()
advanceUntilIdle()
assertFalse(vm.uiState.value.isLoading)

Without a suspension point, a fake starts and finishes within one dispatcher step and there is no "while loading" state to assert on at all.

11. Questions you will be asked, with answers

These are the questions a reviewer or interviewer actually asks about this project. Each answer is short enough to say out loud.

Why Jetpack Compose instead of XML layouts? The spec allowed either.

Compose is Google's recommended approach for new apps and removes an entire bug class: in XML the view state and the data are two things kept in sync by hand, and forgetting one setEnabled(true) on one error path leaves a button dead forever. In Compose the UI is derived from state, so they cannot disagree. It also makes a screen previewable without an emulator.

Why is there no org.jetbrains.kotlin.android plugin?

Since AGP 9.0, Kotlin support is built into the Android Gradle Plugin, and applying that plugin now fails the build with an explicit error. Compiler options moved to a top-level kotlin { compilerOptions { } } block. Nearly every tutorial online still shows the old form.

Why not Hilt for dependency injection?

The app has one dependency worth injecting. Hilt would add an annotation processor, a plugin, modules and six annotations to solve a 20-line problem, and its generated code hides the object graph. Manual DI is an officially documented Android approach; the property that matters — centralised construction — holds either way. For a multi-module app with many dependencies, Hilt would be the right call.

Why does login say "Incorrect email or password" instead of telling the user which one was wrong?

Because distinguishing them turns the login screen into an account-enumeration oracle: feed it a list of addresses and the error messages sort them into registered and unregistered. Two unit tests exist specifically to stop someone adding a "more helpful" message later.

The password-reset screen says it sent a link even for addresses that do not exist. Is that a bug?

No, it is the same defence. A definite "no such account" would confirm which addresses are registered. The user sees an identical response either way, and the wording — "If an account exists..." — is honest rather than false.

Where is the password actually stored?

Nowhere. In Firebase mode it never persists on the device at all — it goes over HTTPS and Firebase hashes it with scrypt server-side. In offline mode only a PBKDF2-HMAC-SHA256 digest is stored, at 210,000 iterations with a unique 16-byte random salt per account. You can read the file off the device and see that for yourself.

Why PBKDF2 and not bcrypt or Argon2?

PBKDF2 ships in the Java standard library, so it needs no third-party dependency and runs unchanged on a server. Argon2id is the stronger modern choice and would be preferable for a real custom backend — but this path is the offline fallback, and the production path delegates hashing to Firebase entirely.

What stops someone reading the encrypted session off a rooted phone?

They can read the ciphertext. The AES-256 key is generated inside the Android Keystore — on most modern devices inside hardware — and is never returned to the app process. We hold an opaque handle and ask the system to decrypt for us. The key cannot be extracted or used on another device, so the ciphertext is inert off that handset.

What happens if the user presses Back after logging out?

They exit to the launcher. Logout navigates with popUpTo(0) { inclusive = true }, which clears the entire back stack, so there is physically nothing behind the Welcome screen. This was verified on the emulator, and it is the most common way an auth flow leaks a protected screen.

How is the Home screen protected?

Not by a check inside the screen. AuthNavGraph observes SessionViewModel.authState and redirects whenever it changes. Centralising it means a new protected screen is protected by default rather than only if someone remembers to add a check.

Why does the app work without a Firebase project?

Both backends implement the same AuthRepository interface. FirebaseApp.initializeApp() returns null when there is no configuration, and ServiceLocator falls back to the offline implementation. Dropping google-services.json into app/ switches to real Firebase with no code change — one file decides the backend.

Why is 210,000 iterations the right number?

It is OWASP's current floor for PBKDF2-HMAC-SHA256. It costs roughly 100ms on a mid-range phone — unnoticeable on a login screen, and expensive to brute force. The iteration count is stored inside each hash so the number can be raised later without invalidating existing accounts.

What would you do differently for production?

Four things, in order: extract the remaining inline UI strings into strings.xml for localisation; add Compose UI tests using the testTags that are already in place; add instrumented tests for KeystoreCrypto and PasswordHasher, which cannot run on the JVM; and add rate limiting plus an offline-detection banner. If the custom-backend route were taken instead of Firebase, hashing would move server-side with Argon2id.

What is the weakest part of this implementation?

The offline mode. It is genuinely useful for demonstration and uses real cryptography, but accounts live only on one device, password reset can only log a link rather than email it, and hashing happens on the device, which does not satisfy spec 5's server-side clause. It is a development and demo affordance, not a production backend — and the code says so in its own class comment.
